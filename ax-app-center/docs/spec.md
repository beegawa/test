## 0. Claude Code 작업 지침

이 문서 하나로 구현을 시작할 수 있게 썼다. 작업할 때 아래 원칙을 지킨다.

- 새 화면을 개발하지 않는다. 웹앱, SPFx, Power Apps, 프리미엄 커넥터를 쓰지 않는다. SharePoint 사이트, Microsoft Lists, Lists 양식, Power Automate 표준 커넥터만 쓴다.
- 스크립트는 멱등하게 쓴다. 두 번 실행해도 결과가 같아야 한다. 대상이 있으면 건너뛰거나 갱신하고, 지우고 다시 만들지 않는다.
- 삭제는 하지 않는다. 사이트, 목록, 열, 항목을 지우는 코드는 넣지 않는다. 필요하면 사람에게 요청한다.
- 테스트 사이트에서 먼저 돌린다. `config.json`의 `environment`가 `test`일 때는 URL 끝에 `-test`가 붙은 사이트에만 쓴다. 운영 배포는 사람이 `prod`로 바꾼 뒤에만 한다.
- 비밀 값을 저장소에 넣지 않는다. 로그인은 대화형으로만 한다. 인증서, 클라이언트 시크릿, 비밀번호를 파일에 쓰지 않는다.
- cmdlet 매개변수는 설치된 버전에서 확인한다. 이 문서의 명령 예시는 방향을 보여 주는 것이다. 실행 전에 `Get-Help <cmdlet> -Full`로 확인한다.
- 확인하지 못한 사항은 8장에 적혀 있다. 그 항목은 구현 중 직접 검증하고 결과를 `docs/verification-log.md`에 남긴다.
- 사람이 정할 값은 9장에 있다. 비어 있으면 추측하지 말고 물어본다.

## 1. 목표

법인·팀이 AI 코딩 도구로 만든 업무 프로그램을 한 곳에 등록하고, 위험 등급에 따라 검토하고, 전 법인이 찾아 쓸 수 있게 한다.

| 정책 장치 | 이 시스템에서의 구현 |
|---|---|
| 등록제 | Lists 양식으로 제출, `프로그램 등록부` 목록에 저장 |
| 위험 등급제 | 제출 답변으로 등급 자동 판정, 등급별 승인 흐름 |
| 사내 앱 카탈로그 | 같은 목록의 `카탈로그` 보기를 사이트 홈에 게시 |
| 운영 체계 | 사이트 권한 그룹과 Power Automate 승인 담당자로 반영 |

이 문서의 범위 밖: 표준 개발·배포 환경(코드 저장소, 공용 실행 환경) 구축, 성과 대시보드.

## 2. 전제

- 본사와 해외 법인이 같은 M365 테넌트를 쓴다. 사이트 하나, 목록 하나로 전 법인을 다룬다.
- 직원 전원이 조직 계정으로 SharePoint에 접근한다. 외부 사용자는 대상이 아니다.
- 구현자는 SharePoint 사이트를 만들 권한이 있고, Entra ID 앱 등록을 할 수 있거나 IT가 대신 해 준다.

### 2.1 실행 환경

| 항목 | 요구 사항 |
|---|---|
| PowerShell | 7.4.0 이상 |
| 모듈 | `PnP.PowerShell` (`Install-Module PnP.PowerShell -Scope CurrentUser`) |
| 앱 등록 | PnP PowerShell용 Entra ID 앱. 2024년 9월 9일부터 테넌트별 자체 등록이 필수 |
| 등록 명령 | `Register-PnPEntraIDAppForInteractiveLogin -ApplicationName "PnP.PowerShell" -Tenant <tenant>.onmicrosoft.com` |
| 등록 권한 | Application Developer 이상. 권한 동의에 전역 관리자가 필요할 수 있음 |
| 연결 | `Connect-PnPOnline -Url <siteUrl> -ClientId <clientId> -Interactive` |

앱 등록은 IT가 한 번만 한다. Claude Code는 등록을 시도하지 않고, `config.json`의 `clientId`가 비어 있으면 멈추고 안내한다.

## 3. 구현 범위: 자동과 수동

| 구성 요소 | 방식 | 담당 |
|---|---|---|
| 사이트 생성 | 스크립트 | Claude Code |
| 목록, 열, 보기, 버전 관리 | 스크립트 | Claude Code |
| 권한 그룹과 목록 권한 | 스크립트 | Claude Code |
| 사이트 페이지(홈, 등급 기준) | 스크립트 | Claude Code |
| 테스트 데이터, 검증 스크립트 | 스크립트 | Claude Code |
| 전수 조사 결과 CSV 가져오기 | 스크립트 | Claude Code |
| Lists 양식(등록 화면) | 화면에서 수동 | GBI팀. 절차서는 Claude Code가 작성 |
| Power Automate 흐름 3개 | 화면에서 수동 | GBI팀. 단계별 명세는 Claude Code가 작성 |
| 사용자 안내서, 관리자 안내서 | 문서 | Claude Code |

양식과 흐름을 수동으로 두는 이유: Lists 양식을 만드는 공개 API를 확인하지 못했고, 흐름을 코드로 만드는 방법은 Dataverse 환경과 솔루션 구성을 전제로 해 이 프로젝트 규모에 비해 무겁다.

## 5. 설계

### 5.1 사이트

- 종류: 커뮤니케이션 사이트 (M365 그룹 없음)
- URL: `https://<tenant>.sharepoint.com/sites/ax-app-center`
- 기본 언어: 한국어(1042)
- 명령 방향: `New-PnPSite -Type CommunicationSite -Title ... -Url ... -Lcid 1042`

### 5.2 권한

| 그룹 | 구성원 | 사이트 | 등록부 | 변경 신청 | 자료 라이브러리 |
|---|---|---|---|---|---|
| AX 앱 센터 소유자 | GBI팀 | 모든 권한 | 모든 권한 | 모든 권한 | 모든 권한 |
| AX 검토자 | 법인별 AX 담당자, 보안 담당, 시스템 담당 | 읽기 | 편집 | 편집 | 편집 |
| AX 앱 센터 방문자 | 외부 사용자를 제외한 모든 사용자 | 읽기 | 읽기 | 읽기 | 읽기 |

핵심 결정: 일반 직원은 등록부를 직접 수정하지 못한다. 등록은 양식으로, 변경은 변경 신청 양식으로 한다.
이유: SharePoint에는 열 단위 권한이 없다. 직원에게 본인 항목 편집 권한을 주면 확정 등급과 상태까지 스스로 바꿀 수 있다.

구현 메모:
- 등록부, 변경 신청, 자료 라이브러리는 권한 상속을 끊고 위 표대로 부여한다.
- "외부 사용자를 제외한 모든 사용자"는 클레임 `c:0-.f|rolemanager|spo-grid-all-users/<tenantId>` 형식이다. 테넌트 ID는 연결 후 조회한다.
- (구현) 소유자·방문자 그룹은 사이트에 연결된 기본 그룹을 쓴다. 세 목록에서는 사이트 기본 구성원(Members) 그룹의 권한을 뺀다. 역할 이름은 사이트 언어로 번역되어 있어 RoleTypeKind로 찾는다.

### 5.3 목록 1: 프로그램 등록부

- 표시 이름: `프로그램 등록부`
- URL: `Lists/AppRegistry`
- 버전 관리: 사용, 주 버전 50개 보관
- 첨부 파일: 사용 안 함
- 등록번호: 목록의 기본 `ID` 열을 쓴다

#### 등급 자동 판정

정책 문서의 등급 기준을 그대로 수식으로 옮긴다.

| 등급 | 조건 |
|---|---|
| C | 개인정보·단가·재무 데이터 사용, 또는 ERP·MES에 데이터 입력, 또는 사용 범위가 법인 간 공용 |
| B | C가 아니고, 내부 업무 데이터 사용 또는 사용 범위가 본인만이 아님 |
| A | 그 외 (본인만 사용, 민감 데이터 없음) |

```
=IF(OR([HasSensitiveData],[WritesToCore],[UserScope]="법인 간 공용"),"C",
 IF(OR([HasInternalData],[UserScope]<>"본인만"),"B","A"))
```

- 수식의 문자열은 `config`의 선택지 문자열에서 만들어 넣는다. 한/영 병기를 쓰면 병기된 문자열 전체와 비교해야 한다.
- 계산 열은 `Add-PnPFieldFromXml`로 만든다. 열은 영문 내부 이름으로 먼저 만들고 표시 이름은 나중에 바꾼다.
- 계산 열 생성이 실패하면 `AutoGrade`를 일반 선택 열로 만들고 흐름 F1에서 같은 규칙으로 채운다.

#### 보기

| 보기 | 조건 | 주요 열 | 정렬 |
|---|---|---|---|
| 카탈로그 | 상태 = 승인 | 프로그램명, 용도 설명, 법인, 팀, 만든 사람, 확정 등급, 사용 범위 | 프로그램명 |
| 검토 대기 | 상태가 접수, 검토 중, 보완 요청 | ID, 프로그램명, 법인, 자동 판정 등급, 상태, 검토자, 등록일 | 등록일 오름차순 |
| 법인별 | 전체, 법인으로 묶음 | 프로그램명, 팀, 확정 등급, 상태 | 법인 |
| 점검 예정 | 상태 = 승인, 다음 점검일이 오늘+30일 이내 | 프로그램명, 만든 사람, 책임 팀장, 다음 점검일 | 다음 점검일 |
| 내 프로그램 | 만든 사람 = 나 | 프로그램명, 상태, 확정 등급, 검토 의견 | 등록일 내림차순 |
| 전체(관리) | 전체 | 모든 열 | ID 내림차순 |

기본 보기는 `카탈로그`로 한다.

**구현 메모:** 보기 URL은 영문(`Catalog.aspx`, `ReviewQueue.aspx`, `ByEntity.aspx`, `ReviewDue.aspx`, `MyApps.aspx`, `AdminAll.aspx`)으로 만들고 제목만 한국어로 바꾼다. `점검 예정`은 기한이 이미 지난 항목도 함께 보이도록 `다음 점검일 <= 오늘 + reminderDaysBefore`로 했다.

### 5.4 목록 2: 변경 신청

표시 이름: `변경 신청`, URL: `Lists/ChangeRequests`

| 내부 이름 | 표시 이름 | 형식 | 필수 | 값 |
|---|---|---|---|---|
| `Title` | 요청 제목 | 한 줄 텍스트 | 예 | |
| `AppRegNo` | 등록번호 | 숫자 | 예 | 등록부의 ID |
| `RequestType` | 유형 | 선택 | 예 | 정보 변경, 담당자 변경, 등급 재판정, 사용 중단, 폐기 |
| `Detail` | 변경 내용 | 여러 줄 텍스트(일반) | 예 | |
| `RequestStatus` | 처리 상태 | 선택 | — | 접수, 처리 완료, 반려. 기본값 접수. 양식에서 제외 |
| `HandledBy` | 처리자 | 사용자 | — | 양식에서 제외 |
| `HandledNote` | 처리 의견 | 여러 줄 텍스트(일반) | — | 양식에서 제외 |

등록번호를 조회(Lookup) 열이 아닌 숫자로 두는 이유: Lists 양식이 조회 열을 지원하지 않는다.

### 5.5 문서 라이브러리: 프로그램 자료

- 표시 이름: `프로그램 자료`, URL: `AppDocs`
- 용도: B·C등급 프로그램의 설명서와 검토 결과. 검토자 이상만 올린다.
- 열: `AppRegNo`(숫자). 폴더는 만들지 않고 등록번호로 필터한다.
- 프로그램 코드 자체는 여기 두지 않는다. 등록부의 `코드·파일 위치`에 경로만 적는다.

### 5.6 사이트 페이지

| 페이지 | 구성 |
|---|---|
| 홈 | 한 줄 소개, `프로그램 등록하기` 버튼, `변경 신청하기` 버튼, 등록부 `카탈로그` 보기 웹 파트, 문의처 |
| 등급 기준과 절차 | 등급 표, 등록부터 승인까지의 순서, 임시 보안 수칙 |

- 버튼 링크는 양식을 만든 뒤에 생긴다. 스크립트는 자리 표시 링크로 만들고, `docs/manual-form.md`에 교체 절차를 적는다.
- 명령 방향: `Add-PnPPage`, `Add-PnPPageTextPart`, `Add-PnPPageWebPart -DefaultWebPartType List`

**구현 메모:** 기존 `Home.aspx`는 고치지 않고 새 페이지 `AppCenterHome.aspx`를 만들어 사이트 홈으로 지정한다. 등급 기준 페이지는 `GradeCriteria.aspx`.

### 5.7 Lists 양식 (수동)

`docs/manual-form.md`에 화면 순서대로 적는다. 들어갈 내용:

1. 등록부 목록에서 양식을 새로 만든다. 제목은 `프로그램 등록`.
2. 5.3의 "등록자가 입력하는 열"만 켠다. 검토자 열은 모두 끈다.
3. 양식 설명에 다음 문구를 넣는다.
   - 실제 업무 데이터, 계정, 비밀번호, API 키는 적지 않습니다.
   - 답변에 따라 등급이 자동 판정됩니다.
4. 링크를 복사해 홈의 `프로그램 등록하기` 버튼에 넣는다.
5. 변경 신청 목록도 같은 방법으로 양식을 만든다.

알려진 한계: 조건 분기 없음, 조회 열 미지원, 한 사람의 중복 제출을 막을 수 없음.

### 5.8 Power Automate 흐름 (수동)

공통 규칙:
- 표준 커넥터만 쓴다: SharePoint, 승인, Office 365 Outlook, Teams.
- 흐름 소유자는 개인이 아닌 공용 계정으로 하고 GBI팀 전원을 공동 소유자로 넣는다. 개인 소유 흐름은 담당자가 떠나면 멈춘다.
- 각 흐름 문서(`docs/flows/*.md`)에는 트리거, 동작 순서, 각 동작의 입력 값, 조건식, 메일 문안을 적는다.

#### F1 접수와 분류

트리거: 등록부에 항목이 만들어질 때. 수정에는 반응하지 않게 해 무한 반복을 막는다.

| 자동 판정 등급 | 처리 |
|---|---|
| A | 상태를 승인으로, 확정 등급 A, 승인일 오늘, 다음 점검일 +12개월. 만든 사람과 책임 팀장에게 등록 완료 메일 |
| B | 상태를 검토 중으로. GBI팀(`people.owners`)에 승인 요청(먼저 응답한 사람 기준), 해당 법인 AX 담당자에게는 참조 알림. 결과에 따라 승인 또는 반려로 갱신하고 의견을 검토 의견에 기록 |
| C | 상태를 검토 중으로. 순서대로 승인: 보안 담당 → 시스템 담당 → GBI팀. 한 단계라도 반려되면 반려로 갱신 |

- C등급의 시스템 담당은 `연결 시스템` 값으로 정한다: ERP 포함이면 ERP 담당, MES 포함이면 스마트팩토리 담당, 그 외는 SI 담당. 둘 다 포함이면 두 사람 모두 승인해야 한다.
- 승인되면 확정 등급에 자동 판정 등급을 넣는다. 검토자가 등급을 바꾸려면 등록부에서 직접 고친다.

#### F2 변경 신청 알림

트리거: 변경 신청에 항목이 만들어질 때. GBI팀 메일과 Teams 채널에 등록번호, 유형, 내용을 알린다.

#### F3 정기 점검 알림

트리거: 매주 월요일. 상태가 승인이고 다음 점검일이 `reminderDaysBefore`일 이내인 항목을 찾아, 만든 사람과 책임 팀장에게 점검 요청 메일을 보낸다. 검토 중 상태로 `slaBusinessDays`가 지난 항목은 GBI팀에 따로 알린다.

### 7.2 권한 (사람이 확인)

- 읽기 권한만 있는 계정으로 양식 제출이 되는가.
- 같은 계정으로 등록부 항목을 직접 수정할 수 없는가.
- 검토자 계정으로 상태와 확정 등급을 바꿀 수 있는가.
- 해외 법인 계정으로 홈과 카탈로그가 열리는가.

### 7.3 흐름 (사람이 확인)

A, B, C 각 한 건씩 제출해 상태 변화, 승인 요청 수신자, 메일 수신자를 확인한다. C는 중간 단계에서 반려했을 때 상태가 반려로 끝나는지도 본다.

## 8. 확인하지 못한 사항

구현 중 직접 검증하고 `docs/verification-log.md`에 결과를 적는다.

| 항목 | 확인할 것 | 안 될 때의 대안 |
|---|---|---|
| 양식 제출 권한 | 목록 읽기 권한만으로 Lists 양식 제출이 되는지 | 방문자에게 항목 추가 권한을 주고 목록의 쓰기 보안을 `WriteOnlyMyItems`로. 이 경우 본인 항목의 등급·상태 수정을 F1에서 되돌리는 처리가 필요 |
| 양식의 열 지원 | 사용자 열, 복수 선택 열, 예/아니오 열이 양식에 나오는지 | 지원되지 않는 열은 한 줄 텍스트나 단일 선택으로 바꿈 |
| 계산 열 | 예/아니오 열을 참조하는 수식이 한국어 사이트에서 동작하는지 | 5.3의 대안대로 F1에서 등급 계산 |
| 한/영 병기 | 병기한 선택지 문자열이 수식과 보기 필터에서 문제없는지 | 선택지는 한국어만, 열 이름만 병기 |
| 목록 웹 파트 | 스크립트로 넣은 웹 파트가 지정한 보기를 보여 주는지 | 홈에는 보기 링크 버튼만 두고 웹 파트는 수동 추가 |
| 기본 승인 기능 | 목록의 기본 승인 기능이 F1을 대신할 수 있는지 | 쓰지 않음. 등급별 분기가 필요해 F1로 구현 |
| 라이선스 | 회사 요금제에 Power Automate 표준 커넥터와 승인이 포함되는지 | IT에 확인 |
